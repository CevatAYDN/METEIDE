# @mete/ui-theia

The Theia extension of METE IDE: its commands and panels, and the connection to the core daemon (ARCHITECTURE, Daemon protocol; ADR-045). Layer 6. `apps/desktop` depends on it, because Theia collects extensions only from the dependencies of the application package.

Modules: none (not a MeteModule)

## What it contains

- A frontend module with one command, "METE: Status" in the command palette (docs/13, Design system). It asks the backend for the runs of the first open folder and shows their count and the newest five by status and goal, "Open a folder first" without a folder, or why the daemon gave none: it is not ready (what core-engine waits for, ADR-046), it stopped or keeps stopping (its exit code and last stderr lines), it refused, or its answer did not parse.
- "METE: Quota" (ADR-050): it asks the daemon of the first open folder with `mete/quota` and says each provider's state: ready, no key (with "METE: Set provider key"), not active, its free quota used up until a time, or none of its models usable here, in the words of the CLI's quota-pause lines. Under a run paused for quota the Home view lists the providers that are not ready, asked only while such a run exists; a failed ask leaves the lines out and "METE: Quota" names why. The lines follow `run.*` events, so a second provider running out during the pause shows on the next run event or Refresh. Checked in the window: on a folder with no run, "METE: Quota" named nvidia unusable (privacy rules), openrouter and groq ready, opencode-zen and google without a key, as `mete key list` says (shortcut: the used amount, limit and history per unit of the docs/13 quota dashboard need a quota pool read, ADR-050).
- The Team panel (docs/13, ADR-051): "METE: Open team panel" lists the first open folder's runs (goal, status and team) and shows the one picked in the main area, its tasks in To do, In progress and Done by status, with In review, Changes asked or Blocked on the cards that wait in In progress. The panel listens first and buffers the run's live events, reads its history with `mete/events`, folds it with `@mete/ui-studio`, then the buffer, then each live event; the fold applies an event id once, so the overlap is harmless and a status change never lands before its task. It names how many events could not be read, and says a single-agent run has no board. Checked in the window on the Phase 4 gate run's folder: the pick listed the completed web-dev run, and the Board showed its three tasks in Done with their roles A Board / Flow switch draws the same run as a graph instead: React Flow (docs/05, `@xyflow/react`, read only) with a node per task, one level after the deepest task it waits for, an edge per `dependsOn`, and the border colour of its Board column (the layout is small own code: React Flow has none, and a layout library is not in docs/05). A third mode, Studio (ADR-052), draws the run as the studio room of `@mete/ui-studio` on a PixiJS canvas that follows its box's width, the cozy office of the approved demo in its own colours (ADR-070), scaled from the room's own space (a click is scaled back before it is tested), with the run's seven latest events of the docs/13 studio table listed under it (`aria-live`), one sentence each, in the words of what the room shows (`studio-text.ts`). Each live event the fold takes (never one from the history or the buffer) plays its effects over the room: the session keeps it with the view before it, and the stage stops while the panel is hidden. Checked in the window on the gate run: the four lead agents (each review has its own agent) sit in the top row, the designer, developer and QA below, three notes in Done; the Dark theme recoloured the stage and Light was restored; one free single-agent run ("Reply with the single word done", a few OpenRouter free requests) showed its one desk and the sentences, though it ended before the panel opened, so the live effects rest on the tests; switching Board and Studio more than forty times left one canvas with its WebGL context alive and no console warning (each Studio mount makes a context and its unmount destroys it) (shortcut: sprites and the rows whose events no module publishes yet come with the theme module). A click on the Studio's coffee corner runs "METE: Open quota dashboard" (docs/13, Interaction; `inside` of `@mete/ui-studio` tests the point against the layout's corner, and the pointer cursor marks it); checked in the window on the gate run: with the Quota tab closed, a click on a desk opened nothing and a click on the corner opened the dashboard (shortcut: notes and characters take no click yet: there is no task view, and the character card needs the tier and request count the fold does not carry). Its stylesheet import is why `src/css.d.ts` exists, and only the frontend loads that file. Checked in the window on the gate run: Flow drew its three tasks left to right with two edges on the theme's background (shortcut: agent cards and nodes and the Studio come later; cards show the role id, not the role name docs/13 asks for, because `task.created` carries only the id: names come when the daemon offers the run's template).
- The Audit log (docs/13; SECURITY.md, Audit log; ADR-053): "METE: Open audit log" lists the first open folder's policy decisions newest first (time, action, capability, verdict, rule) from `mete/audit`, filtered by run (the folder's runs by goal), verdict and action, and asks again on Refresh, a filter change and every `run.*` event. "Export as JSON…" writes the rows shown to a file the user picks in the system's save dialog (`auditJson`, tested in Node; the native dialog itself is not driven by the window checks). Checked in the window on the gate run's folder: nine rows (four `shell.exec`, five `fs.write`, all allowed), the deny filter gave the empty sentence and disabled Export, and the `shell.exec` filter left four rows.
- The Quota dashboard (docs/13; ADR-054): "METE: Open quota dashboard" lists the `units` of the first open folder's `mete/quota` answer in the main area, one row per provider, unit and model scope ("Every paid model" for the daily spending cap) with used, limit ("Not known yet" before a discover unit learns one) and reset time, and asks again on Refresh and every `quota.*` event of its folder. The units are the daemon's own pool: a run started from a terminal counts in that process (ADR-054). Checked in the window on the gate run's folder: five rows from the real pool (the spending cap, NVIDIA and OpenRouter per minute, OpenRouter 14 of 50 a day loaded from `mete.db` with the next 00:00 UTC reset, Groq with its learned limit of 4), read only. A History column folds each unit's amounts in the window under their count, each with its time, oldest first (ADR-055; a list, since a chart is a visual decision left to the user). Checked in the window: the OpenRouter day row folds three amounts (7, 5 and 2, making its 14: a `remaining` read from a response sets the usage, docs/09), the others a dash.
- "METE: Start run", the run composer (ADR-047, ADR-058, ADR-071), and the METE view's New run button show the composer in the Team panel, which also shows it while it shows no run, and a fresh layout opens the panel in the main area (ADR-078; `run-composer.tsx` keeps its state and requests, the panel draws it): a goal field (a text area with the cursor in it; Ctrl+Enter starts), then the teams to pick one of ("Let METE choose", each template `mete/templates` lists by name with its description, "Single agent"), each team and the single agent with its `mete/estimate` line under it, such as "45 requests: nvidia 36 · groq 9", where a team's line adds that tasks the team adds come on top (ADR-068), and a Start button that stays disabled while the goal is blank or a start is under way. The templates and estimates are asked again every time the composer is shown or its panel is activated. Start sends `mete/run.start` for the first open folder, says "Run started" and the same panel turns into the run; while the router picks a team, the screen says METE is starting the run (the router decides before the run exists, docs/08, so the daemon has nothing to send until then, which can take a minute on free models; an earlier signal would change docs/08); when the router is unsure the list narrows in place to its suggested teams and "Single agent", and Start again starts with the one picked; a failed start shows its reason under the button. The list and the request are plain functions (`application/composer.ts`, tested on Node); the screen is a stateless React view (`composer-view.tsx`). shortcut: the autonomy level of docs/13 stays off the screen until a per-run level exists that policy.check can take (ADR-071). A run that pauses for approval is answered in the Home view's inbox.
- "METE: Set provider key", the first onboarding step (ADR-049): it offers the providers `mete key list` names, each with whether it has a key, asks for the key in a masked field and saves it through `mete key set <id>` run by the backend on its own Node, with the key on standard input only, so it lands in the keychain the CLI and the daemon read; then the backend restarts the folder's daemon, which reads it. While METE is not ready the Home view offers "Set provider key…". The Home view asks again whenever that command ran, from the palette or its button. A failing `mete key` is named as such, not as a daemon refusal. The key crosses Theia's frontend-to-backend channel once, a local connection like the one Theia's own credential service uses (shortcut: the wizard's language, privacy choice, vault folder and web search steps of docs/13 come later).
- The approvals inbox (ADR-048): the "Waiting for you" section at the top of the METE view with the runs paused for approval. A team run offers Approve, Revise… (feedback in a quick input) and Resume; a single-agent run offers only Resume, with the hint that Resume repeats the tool call the policy asked about, so the run stops again unless `.mete/policy.yaml` allows it (the inbox never edits the policy). The buttons run "METE: Approve run", "METE: Revise run" and "METE: Resume run", which ask which waiting run when the palette starts them. The engine judges every answer: the task is left out, so the engine takes the only one that waits, and a refusal shows the engine's message A team run's row also offers Open artifact ("METE: Open artifact", which asks which run from the palette): it reads the run's history with `mete/events`, folds it, and opens the report of the task under review, else the latest report, in an editor. Checked in the window on the gate run's folder: the palette asked for the run and opened the web-dev run's `test.md` from `.mete/artifacts/` in an editor tab (shortcut: the diff and clarifications of docs/13 come later). The METE view's side-bar icon carries the inbox badge of docs/13: the count of runs that wait for you, set by a tab bar decorator (`inbox-badge.ts`) each time the store gets an answer, and hidden at zero. Checked in the window on the gate run's folder, where nothing waits: no badge and no console error; a count above zero needs a run paused for approval, which needs model calls, so it rests on the `waitingCount` and `inbox-badge` tests.
- The METE view in Theia's left side bar (docs/13, Home; ADR-078), a view container like the Explorer, ranked above it, opened on a fresh layout, once in a layout saved before it, and by "METE: Open home"; "METE: Refresh home" and its Refresh button ask again. One store (`home-store.ts`) asks the first open folder's daemon and feeds four collapsible sections: Waiting for you (the approvals inbox; the part is hidden while nothing waits and shown when a run starts waiting), Runs (each run with a status chip, its goal, template and creation time; a goal opens its run in the Team panel, "METE: Open team panel" with the run id; New run opens the composer; under a quota pause the providers that block it and Resume now, under a user pause Resume; or "Open a folder first", or the reasons of "METE: Status"), Workspaces (the folders Theia remembers, newest first, the open one marked "(open)", each path one line cut with an ellipsis and whole in the tooltip) and Quota (a chip per provider, coloured by state, its tooltip in the words of "METE: Quota", a click opening the Quota dashboard). It asks again on every `run.*` event of its folder and after a key is set. Runs marks the run the Team panel shows (`aria-current`, through the `shown-run.ts` singleton the panel writes). While a run waits, the status bar shows "N waiting for you" beside Stop all, which runs "METE: Show what waits for you": it opens the METE view on Waiting for you, also when the user had hidden or collapsed it (`waiting.ts`; the count and the Waiting part change only when the count does, which `test/waiting.test.ts` drives with a fake store, since no run waited in the window check). The menu bar has a METE menu before Help: Start run and Open team panel; Open quota dashboard, Open audit log and Edit team; Stop all (ADR-078). The view is TSX on the automatic runtime. Every METE panel's root takes the design system of docs/13 (ADR-069): the tokens of `@mete/ui-kit` in Theia's light and dark themes, none in a high-contrast theme, where each style's Theia fallback applies, and Baloo 2 from `style/mete.css`, which the bundle inlines with its font (`fonts/`, THIRD_PARTY_NOTICES.md).
- A backend module with one RPC service (`/services/mete-daemon`, methods `status`, `events`, `audit`, `quota`, `templates`, `estimate`, `startRun`, `approve`, `resume`, `stopAll`, `keys` and `setKey`). Every frontend that connects passes a client, and the backend forwards each `mete/event` of a daemon to all of them with its folder, after checking it against the event catalog (an event that does not parse is logged as a protocol fault); a frontend leaves the set when its connection closes. The backend owns the daemon: the first call for a folder starts `mete daemon <folder>` on its own Node with `ELECTRON_RUN_AS_NODE=1`, one folder at a time (another folder replaces it), and the backend closes its input on exit, which is how a daemon is asked to stop. The daemon is started detached: on Windows a child that is not sits in its parent's job object and is killed the moment the desktop quits or crashes, before it can stop and free the run lock (checked on Windows 11 under Node and Electron). Detached, it outlives the desktop, sees its input close and stops itself within a second, freeing the lock; a run that was running is then paused with reason `user` on the next start until it is resumed (docs/07, recovery). A daemon that ended on its own starts again at most 3 times in 5 minutes (ARCHITECTURE, Failure handling): at once when it had answered a request, so its runs resume, and on the next call when it ended before answering (a held run lock, an invalid configuration), so the user can fix the cause first; past the limit the next call returns the reason it gave.
- Every label and message goes through `nls.localize` (docs/05, Localization), in English and Turkish (docs/13). English is the default and lives in the code; `i18n/nls.json` is its extract (`pnpm --filter @mete/desktop exec theia nls-extract -r ../../packages/ui-theia/src -f "**/*.{ts,tsx}" -o ../../packages/ui-theia/i18n/nls.json`, then `pnpm exec biome check --write packages/ui-theia`, because the extractor writes two-space JSON and Biome wants tabs), and `i18n/nls.tr.json` is the Turkish file, written by hand; the backend registers it with Theia's localization registry. `test/i18n.test.ts` fails when a key the code uses is missing from either file or a `{n}` placeholder is lost, so the files keep up with the code. The Turkish file registers as a language pack, because Theia lists a language in "Configure Display Language" only then; Theia's own Turkish texts join it, but the menu bar and the other labels Theia takes from VS Code stay English (shortcut: they need a VS Code Turkish language pack, a new dependency and so an ADR). Checked in the window: Türkçe switches the METE commands and the Home view, and English switches them back. Commands are written out one by one (no helper), so the extractor can read their labels. The CLI stays English (docs/05 gives core messages to i18next, a separate mechanism).

Without a provider key the daemon still starts and the command says METE is not ready yet, with what core-engine waits for; "METE: Set provider key" adds one and restarts the daemon (ADR-046, ADR-049). A run lock held by another `mete` command still stops the daemon, and the command says so.

## Decisions behind the layout

- The package is CommonJS (no `"type": "module"`, `verbatimModuleSyntax` off), because Theia's generated backend loads extension modules with `require` and reads `module.default` (ADR-002). It sets `experimentalDecorators`, because inversify's `@injectable()` and `@inject()` are legacy decorators; `emitDecoratorMetadata` stays off, so every dependency is a property injection, as in Theia's own classes.
- `package.json` has no `exports`: the generated application imports the module files by path (`theiaExtensions`).
- Only `@mete/contracts` may be imported from other METE packages, and only this package and `apps/desktop` may import `@theia/*` (dependency-cruiser rules `desktop-talks-to-the-daemon` and `theia-only-in-ui-theia`). The one `@mete/cli` lookup (`require.resolve` of its `package.json`, to find the `mete` entry file) is a path, not an import, and dependency-cruiser does not follow `require.resolve`, so no rule sees it.
- The backend is bundled into `apps/desktop/lib/backend`, so that lookup starts there: `apps/desktop` depends on `@mete/cli` as well.
- The bundle loads `dist/` of this package and the daemon runs `dist/` of `@mete/cli`, so run `pnpm build` before `pnpm --filter @mete/desktop bundle`.
- React: Theia 1.76 takes `react` as a peer (`^19.0.0`) and `@theia/core/shared/react` re-exports it, so `react` and `react-dom` 19.3.0 are dependencies of this package and of `apps/desktop` at the same exact version (with `@types/react` and `@types/react-dom` 19.3.0 as devDependencies of both): different peer sets would make pnpm build a second `@theia/core` and a second inversify, and the extension would bind into a container nobody reads.
- Tests: the Home view is rendered with `react-dom/server` on Node; the host runs against a fake daemon, a Node script that speaks the daemon protocol over real pipes. The command test replaces two Theia browser modules (they need a DOM) with stubs; the window check covers the real wiring.
