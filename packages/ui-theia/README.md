# @mete/ui-theia

The Theia extension of METE IDE: its commands and panels, and the connection to the core daemon (ARCHITECTURE, Daemon protocol; ADR-045). Layer 6. `apps/desktop` depends on it, because Theia collects extensions only from the dependencies of the application package.

Modules: none (not a MeteModule)

## What it contains

- A frontend module with one command, "METE: Status" in the command palette (docs/13, Design system). It asks the backend for the runs of the first open folder and shows their count and the newest five by status and goal, "Open a folder first" without a folder, or why the daemon gave none: it is not ready (what core-engine waits for, ADR-046), it stopped or keeps stopping (its exit code and last stderr lines), it refused, or its answer did not parse.
- "METE: Start run", the first run composer (ADR-047): it asks for a goal, starts the run in the first open folder through `mete/run.start` and says "Run started"; when the router is unsure it offers the suggested teams and "Single agent" and starts again with the one picked (shortcut: the composer screen of docs/13, with the template picker, the estimate and the autonomy level, comes when the daemon can list templates and estimates). A run that pauses for approval is answered in the Home view's inbox.
- "METE: Set provider key", the first onboarding step (ADR-049): it offers the providers `mete key list` names, each with whether it has a key, asks for the key in a masked field and saves it through `mete key set <id>` run by the backend on its own Node, with the key on standard input only, so it lands in the keychain the CLI and the daemon read; then the backend restarts the folder's daemon, which reads it. While METE is not ready the Home view offers "Set provider key…". The key crosses Theia's frontend-to-backend channel once, a local connection like the one Theia's own credential service uses (shortcut: the wizard's language, privacy choice, vault folder and web search steps of docs/13 come later).
- The approvals inbox (ADR-048): a "Waiting for you" section at the top of the Home view with the runs paused for approval. A team run offers Approve, Revise… (feedback in a quick input) and Resume; a single-agent run offers only Resume, with the hint that Resume repeats the tool call the policy asked about, so the run stops again unless `.mete/policy.yaml` allows it (the inbox never edits the policy). The buttons run "METE: Approve run", "METE: Revise run" and "METE: Resume run", which ask which waiting run when the palette starts them. The engine judges every answer: the task is left out, so the engine takes the only one that waits, and a refusal shows the engine's message (shortcut: the artifact preview, diff, clarifications and the inbox badge of docs/13 come later).
- A Home view in Theia's left side bar (docs/13, Home: recent runs), opened on a fresh layout and by "METE: Open home"; "METE: Refresh home" and its Refresh button ask again. It lists the first open folder's runs by status, goal (with the template) and creation time, says "Open a folder first" without a folder, or shows the same reasons as "METE: Status" (not ready, stopped, keeps stopping, refused, unreadable answer), and names the time of the snapshot. It asks again on every `run.*` event of its folder (shortcut: the workspaces and quota summary of the docs/13 Home row come later). The view is TSX on the automatic runtime with inline styles on Theia's CSS variables (shortcut: the METE tokens and Baloo 2 of docs/13 come with `packages/ui-kit`, which is still empty).
- A backend module with one RPC service (`/services/mete-daemon`, methods `status`, `startRun`, `approve`, `resume`, `keys` and `setKey`). Every frontend that connects passes a client, and the backend forwards each `mete/event` of a daemon to all of them with its folder, after checking it against the event catalog (an event that does not parse is logged as a protocol fault); a frontend leaves the set when its connection closes. The backend owns the daemon: the first call for a folder starts `mete daemon <folder>` on its own Node with `ELECTRON_RUN_AS_NODE=1`, one folder at a time (another folder replaces it), and the backend closes its input on exit, which is how a daemon is asked to stop. Checked on Windows 11: a daemon asked through its input frees its run lock in under 100 ms, but when the desktop quits the daemon is gone within a second and the lock stays, so the quit ends it first; the next start takes the stale lock over (a pid that is no longer alive) and a run that was running becomes paused with reason `user` until it is resumed (docs/07, recovery). A daemon that ended on its own starts again on the next call, at most 3 times in 5 minutes (ARCHITECTURE, Failure handling). (shortcut: a crashed daemon starts again on the next call, not at once.)
- Every label and message goes through `nls.localize` (docs/05, Localization). The Turkish resource file is not written yet (shortcut: it joins the English and Turkish item of Phase 5).

Without a provider key the daemon still starts and the command says METE is not ready yet, with what core-engine waits for; "METE: Set provider key" adds one and restarts the daemon (ADR-046, ADR-049). A run lock held by another `mete` command still stops the daemon, and the command says so.

## Decisions behind the layout

- The package is CommonJS (no `"type": "module"`, `verbatimModuleSyntax` off), because Theia's generated backend loads extension modules with `require` and reads `module.default` (ADR-002). It sets `experimentalDecorators`, because inversify's `@injectable()` and `@inject()` are legacy decorators; `emitDecoratorMetadata` stays off, so every dependency is a property injection, as in Theia's own classes.
- `package.json` has no `exports`: the generated application imports the module files by path (`theiaExtensions`).
- Only `@mete/contracts` may be imported from other METE packages, and only this package and `apps/desktop` may import `@theia/*` (dependency-cruiser rules `desktop-talks-to-the-daemon` and `theia-only-in-ui-theia`). The one `@mete/cli` lookup (`require.resolve` of its `package.json`, to find the `mete` entry file) is a path, not an import, and dependency-cruiser does not follow `require.resolve`, so no rule sees it.
- The backend is bundled into `apps/desktop/lib/backend`, so that lookup starts there: `apps/desktop` depends on `@mete/cli` as well.
- The bundle loads `dist/` of this package and the daemon runs `dist/` of `@mete/cli`, so run `pnpm build` before `pnpm --filter @mete/desktop bundle`.
- React: Theia 1.76 takes `react` as a peer (`^19.0.0`) and `@theia/core/shared/react` re-exports it, so `react` and `react-dom` 19.3.0 are dependencies of this package and of `apps/desktop` at the same exact version (with `@types/react` and `@types/react-dom` 19.3.0 as devDependencies of both): different peer sets would make pnpm build a second `@theia/core` and a second inversify, and the extension would bind into a container nobody reads.
- Tests: the Home view is rendered with `react-dom/server` on Node; the host runs against a fake daemon, a Node script that speaks the daemon protocol over real pipes. The command test replaces two Theia browser modules (they need a DOM) with stubs; the window check covers the real wiring.
