# @mete/desktop

Theia + Electron application. Composition root. Theia is pinned to 1.76.0 (newest release at least 14 days old on 2026-10-21, published 2026-09-24) and Electron to 42.11.12 (published 2026-10-07): Theia 1.76 names 42.8.1, and the newer patch release of the same major closes its sandbox, protocol-handler and code-cache advisories (the audit of 2026-10-23; the overrides in pnpm-workspace.yaml say which fixes still wait for their 14 days, docs/05).

Modules: none (not a MeteModule)

## Run it

```
pnpm install
pnpm build                             # compiles packages/ui-theia (the bundle loads its dist/) and apps/cli (the daemon)
pnpm --filter @mete/desktop bundle     # generates src-gen/ and lib/ with esbuild
pnpm --filter @mete/desktop download:plugins   # fetches the pinned built-in extensions into plugins/ (network, ADR-103)
pnpm --filter @mete/desktop start      # opens the window
```

`pnpm build` does not bundle the application: the bundle is not part of the turbo graph yet, because its inputs and outputs are not known (shortcut: add it when the desktop gets a CI job that can cache `lib/`).

## Test it end to end

`pnpm --filter @mete/desktop test:e2e` (docs/15) drives the built app with Playwright over its own remote-debugging port — `@playwright/test`'s `_electron` wrapper does not see this app's window, `connectOverCDP` does, and no Playwright browser is ever downloaded (`allowBuilds` keeps its postinstall off). One worker, because the app holds the single-instance lock, so no other instance may run while the tests do. Each test gets a fresh git workspace in the temp folder, answers Theia's workspace-trust dialog, and drives METE through the command palette, the keyboard-first way docs/13 asks; the daemon, the panels and the extension host are the real ones. `run-flow.e2e.ts` goes further: it gives the workspace a team file and the app a chat script (`METE_SCRIPTED_CHAT`, ADR-111), so a real run answers from that script with no provider key and no network, and the tests answer the run in the Home inbox, lift a blocked task from the Team panel, and pause a run on a spent provider's day until the reset (ADR-113). The fixture's `files` and `script` options carry the team files, the turns and, when a flow needs it, a narrower quota for the scripted provider. Each test's app also keeps its global folder — counted quota, logs and settings — in a temp path, so the developer's own data stays out of the tests. `axe-core` runs in the page over METE's panels (`.mete-panel`): the tests marked `@a11y` fail on a serious or critical violation.

`pnpm --filter @mete/desktop test:perf` measures what docs/15 guards: it launches the app on this repository a few times (`METE_PERF_RUNS`, default 3), times the shell and the frontend's settled moment, and prints the whole process tree's memory — renderer, backend, extension host, daemon and all — so the baseline and its 10% rule have numbers behind them.

## What the first window contains

Only the Theia shell: the menu bar, the file navigator, the editor, preferences and messages (`@theia/core`, `electron`, `filesystem`, `workspace`, `navigator`, `editor`, `monaco`, `preferences`, `messages`). The METE extension (`@mete/ui-theia`) adds the command "METE: Status": it starts `mete daemon` for the open folder and says how many runs the folder has, or why not: METE is not ready (a provider key is missing) or the daemon is not running (`mete run` holds the folder). "METE: Start run" asks for a goal and starts a run in the folder. "METE: Set provider key" saves a key in the keychain the CLI uses and restarts the daemon. "METE: Quota" says whether each provider can carry a run on now. "METE: Open audit log" lists the policy's decisions, filtered, and exports them as JSON. "METE: Open team panel" shows a run's tasks in To do, In progress and Done, as a graph of what waits for what, or as the studio room of its agents. A Home view in the left side bar lists the runs that wait for you (Approve, Revise, Resume) and the folder's recent runs (a goal opens its run in the Team panel), with why a run paused for quota waits and each provider's quota state, and follows their events ("METE: Open home", "METE: Refresh home"). The terminal ships with ADR-099 (`@theia/terminal`, native `node-pty`), the project search with ADR-101 (`@theia/search-in-workspace`), and the extension host with ADR-103 (`@theia/plugin-ext` + `@theia/plugin-ext-vscode`): it runs the pinned built-in `vscode.git` extension (with `vscode.git-base`, both 1.108.2, the VS Code version of Theia 1.76's monaco), which adds the Source Control view, its commands and the diff editors, as Theia's own git package is gone (`@theia/git` stops at 1.60.2), and, since ADR-104, the five built-in language extensions (`typescript-language-features` with its bundled tsserver, `css-`, `html-`, `json-` and `markdown-language-features`, all 1.108.2), which give TypeScript and JavaScript, CSS, HTML, JSON and Markdown their completions, diagnostics and the Markdown preview. The debugger ships with ADR-105 (`@theia/debug` with the built-in `ms-vscode.js-debug`, which brings `@theia/task`, `@theia/test`, `@theia/output`, `@theia/console`, `@theia/markers`, `@theia/process` and `@theia/variable-resolver` along): F5 is the person at the keyboard running their own code, like a terminal command (ADR-099). The git extension acts as the person at the keyboard, like the terminal (ADR-099): it runs the user's own git and is neither a capability nor audited; an agent's git stays `vcs.git@2` with the policy and the audit log. No marketplace ships: the built-ins are the only plugins, so nothing asks Open VSX at run time (ADR-021); installing more extensions is a later decision. Theia reports one gap per extension generation: the activation events `onEditSession:file` and `onWalkthrough:nodejsWelcome` are not supported, warnings without effect on git or the languages.

## Decisions behind the layout

- The package is CommonJS (no `"type": "module"`, and `verbatimModuleSyntax` is off in its `tsconfig.json`), because Theia's generated application is CommonJS (ADR-002). Every other package stays ESM, except `@mete/ui-theia`, the extension this application loads.
- `src-gen/`, `lib/`, `esbuild.mjs`, `gen-esbuild*.mjs` and `plugins/` are generated and ignored by git, Biome and dependency-cruiser.
- pnpm's strict layout hides packages that Theia's generated files import by name, so two things make them visible: `devDependencies` names the six build packages those files import (`esbuild`, `esbuild-plugin-copy`, `esbuild-plugins-node-modules-polyfill`, `resolve-package-path`, `yargs`, `@theia/bundle-plugin`), and `publicHoistPattern` in `pnpm-workspace.yaml` hoists the `@theia/*` extensions, `reflect-metadata`, `trash` and the native packages. `node-linker` is unchanged. Keep both lists in step with the Theia version when it is raised.
- `pnpm-workspace.yaml` lists every package with an install script. Four are allowed because the bundle needs their `.node` files: `@theia/ffmpeg`, `drivelist` and `native-keymap` (all N-API, so the same binary runs in Node and in Electron and `theia rebuild:electron` is not needed) and `@vscode/windows-ca-certs`, the extension host's proxy agent on Windows, hoisted for `@theia/bundle-plugin` to resolve. Its `binding.gyp` asks for Spectre-mitigated libraries, which a plain Build Tools install lacks; the patch `patches/@vscode__windows-ca-certs@0.3.4.patch` drops that one attribute so it compiles with the same tools as the rest. `keytar` stays off: Theia loads it lazily for its own credential store, and METE keeps secrets in the operating system keychain (docs/05).
- The built-in extensions are pinned by URL in `theiaPlugins` (ADR-103), downloaded by `theia download:plugins` into `plugins/` (gitignored, decompressing with `decompress`, whose advisory has no fixed release; it only unpacks the pinned files at build time) and loaded by the `--plugins=local-dir:plugins` argument of `start`. Raise the pins with the Theia version: they come from the `eclipse-theia/vscode-builtin-extensions` releases, whose version (1.108.2) matches Theia's monaco.
- On Windows the Theia build needs the Visual Studio C++ Build Tools (Theia's own prerequisite), because those packages compile from source. It is a developer-machine tool, never a requirement for people who install METE (`winget install Microsoft.VisualStudio.2022.BuildTools --override "--wait --passive --add Microsoft.VisualStudio.Workload.VCTools --includeRecommended"`). In that step Theia also replaces Electron's `ffmpeg` library with one that has no proprietary codecs and checks it.
